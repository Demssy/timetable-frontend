# Задача для фронтенд-агента: окно настроек солвера

## Цель и расположение

Реализовать окно настроек солвера с редактированием параметров, восстановлением системных значений и управлением именованными наборами настроек.

**Кнопку открытия окна разместить внутри выбранного расписания, непосредственно рядом с существующей кнопкой запуска солвера.** Не переносить её на отдельную страницу общих настроек и не менять существующий способ запуска солвера. Использовать текущие компоненты, стили, локализацию и архитектуру фронтенд-проекта.

Настройки доступны администратору. Окно должно быть доступно из выбранного расписания как для `DRAFT`, так и для `PUBLISHED`, если соответствующая кнопка запуска солвера находится на этом экране. Не создавайте дополнительное ограничение по статусу расписания для настроек.

**Важно:** несмотря на расположение кнопки, настройки глобальные, а не принадлежат конкретному расписанию. Они влияют на новые запуски солвера и последующие проверки расписаний. Покажите это в интерфейсе, чтобы пользователь не считал их настройками только выбранного расписания.

## Поведение окна

1. При открытии загрузить активные настройки и список сохранённых наборов. Показать индикатор загрузки; при ошибке сообщить о ней и предоставить повторную загрузку.
2. Отобразить все 15 активных параметров с понятными названиями, текущими значениями, ограничениями и системными значениями по умолчанию из ответа сервера. Не зашивать значения по умолчанию во фронтенд: они зависят от конфигурации backend.
3. Предоставить редактирование числовых значений и явное сохранение активных настроек. Сохранение отправляет **весь объект из 15 полей**. После успешного ответа обновить форму из ответа сервера и показать результат пользователю.
4. Предоставить восстановление системных значений кнопкой сброса. Эта операция сразу меняет активные настройки на сервере, но не удаляет сохранённые наборы. До выполнения подтвердить сброс, особенно если в форме есть несохранённые изменения.
5. Показать список именованных наборов, выделить активный набор по `activePresetId` и обеспечить создание, изменение имени и значений, выбор/активацию и удаление набора. Создание набора сохраняет текущие значения формы под заданным именем, но **не активирует** его автоматически. Изменение набора сохраняет его имя и полный объект настроек.
6. Активацию набора выполнять отдельным запросом; после успеха заполнить форму активными значениями из ответа. При редактировании активного набора backend также обновляет активные значения. При удалении активного набора текущие значения остаются активными, но связь с набором снимается; после изменения или удаления обновить данные с сервера.
7. Перед закрытием окна, выбором набора или другим действием, которое перезапишет несохранённую форму, предупредить пользователя и дать возможность отменить действие. Перед удалением набора запросить подтверждение.
8. Показать пояснение: изменение настроек **не запускает солвер и не пересчитывает расписание автоматически**. Уже запущенный расчёт продолжает работать со старыми настройками; следующий запуск использует актуальные. Настройки также используются при последующих проверках расписания.

Прямое сохранение активных настроек через `PUT /api/v1/solver/settings` снимает привязку к активному набору и не редактирует сам набор. Не показывать после этого старый набор активным. Если пользователь хочет изменить сохранённый набор, использовать отдельное действие редактирования набора.

## Поля формы

Все поля обязательны и принимают **целые числа**. Для полей без указанного меньшего максимума верхняя граница backend — `2147483647`. Не преобразовывать пустое поле в ноль и не отправлять дробные значения. Блокировать отправку невалидной формы и показывать ошибки у соответствующих полей; серверная проверка также обязательна.

| Поле API | Название в интерфейсе | Диапазон | Пояснение |
|---|---|---|---|
| `solverTimeLimitSeconds` | Время работы солвера, сек. | 5–300 | Ограничение длительности нового расчёта |
| `maxAllowedHardPenalty` | Допустимый hard-штраф при публикации | 0–2147483647 | Сумма взвешенных штрафных баллов, а не количество нарушений |
| `teacherMaxDailyLessons` | Максимум уроков преподавателя в день | 1–2147483647 | Порог для дневного ограничения |
| `teacherBreakThresholdMinutes` | Порог окна преподавателя, мин. | 0–2147483647 | Порог при расчёте штрафа за окна |
| `physicalConflictHardWeight` | Вес физических конфликтов | 1–50 | Hard-штраф |
| `weeklyAvailabilityHardWeight` | Вес нарушения недельной доступности | 1–20 | Hard-штраф |
| `teacherDailyLimitHardWeight` | Вес превышения дневного лимита преподавателя | 0–20 | `0` отключает этот штраф |
| `studentMultipleDailyPrivateHardWeight` | Вес нескольких частных уроков ученика в день | 0–20 | `0` отключает этот штраф |
| `weeklyQuotaOverflowHardWeight` | Вес превышения недельной квоты | 1–20 | Hard-штраф |
| `privateLessonAssignmentReward` | Вознаграждение за назначение ученика | 0–100 | Soft-вознаграждение |
| `primeTimeLessonReward` | Вознаграждение за урок в прайм-тайм | 0–100 | Soft-вознаграждение |
| `studentUnfulfilledLessonPenalty` | Штраф за невыполненный запрос ученика | 0–100 | Soft-штраф |
| `teacherUnfulfilledLessonPenalty` | Штраф за невыполненный запрос преподавателя | 0–100 | Soft-штраф |
| `teacherGapPenaltyMultiplier` | Множитель штрафа за окна преподавателя | 0–100 | Soft-штраф |
| `teacherWorkloadFairnessMultiplier` | Множитель штрафа за дисбаланс нагрузки | 0–100 | Soft-штраф |

Уместно сгруппировать поля на общие параметры, hard-штрафы и soft-штрафы/вознаграждения. Пояснить, что увеличение веса увеличивает число начисляемых штрафных или наградных баллов; настройки soft не заменяют hard-ограничения.

Ненулевой `maxAllowedHardPenalty` разрешает публикацию и последующие изменения опубликованного расписания в пределах общей суммы hard-штрафа. При этом обязательные проверки назначений остаются в силе, а конфликт преподавания и посещения другого урока одним пользователем запрещён независимо от порога.

## Контракт backend API

Базовый путь: `/api/v1/solver/settings`. Все запросы требуют авторизацию пользователя с ролью `ADMIN`; используйте существующий механизм JWT фронтенда. Настройки и наборы не привязаны к `scheduleId`, поэтому не добавляйте его в URL или тело запроса.

| Метод | Путь | Результат |
|---|---|---|
| `GET` | `/api/v1/solver/settings` | Текущие поля, `defaults`, `activePresetId` |
| `PUT` | `/api/v1/solver/settings` | Полная замена активных полей; возвращает тот же формат, что `GET` |
| `POST` | `/api/v1/solver/settings/reset` | Сброс к системным значениям; возвращает тот же формат, что `GET` |
| `GET` | `/api/v1/solver/settings/presets` | Массив наборов |
| `POST` | `/api/v1/solver/settings/presets` | Создание набора; `201` и созданный набор |
| `PUT` | `/api/v1/solver/settings/presets/{id}` | Замена имени и значений набора; возвращает изменённый набор |
| `POST` | `/api/v1/solver/settings/presets/{id}/activate` | Активация набора; возвращает тот же формат, что `GET` настроек |
| `DELETE` | `/api/v1/solver/settings/presets/{id}` | Удаление набора; `204`, без тела ответа |

### Именованные наборы

Тело создания и изменения набора:

```json
{
  "name": "Мой набор",
  "settings": {
    "solverTimeLimitSeconds": 10,
    "maxAllowedHardPenalty": 0,
    "teacherMaxDailyLessons": 6,
    "teacherBreakThresholdMinutes": 15,
    "physicalConflictHardWeight": 1,
    "weeklyAvailabilityHardWeight": 1,
    "teacherDailyLimitHardWeight": 1,
    "studentMultipleDailyPrivateHardWeight": 1,
    "weeklyQuotaOverflowHardWeight": 1,
    "privateLessonAssignmentReward": 100,
    "primeTimeLessonReward": 10,
    "studentUnfulfilledLessonPenalty": 50,
    "teacherUnfulfilledLessonPenalty": 30,
    "teacherGapPenaltyMultiplier": 1,
    "teacherWorkloadFairnessMultiplier": 1
  }
}
```

Ответ набора имеет форму `{ "id": 1, "name": "Мой набор", "settings": { ...15 полей... } }`; список — массив таких объектов. Имя не может быть пустым или состоять только из пробелов, максимальная длина — 120 символов. Backend обрезает пробелы по краям и требует уникальность имени; ошибку дубликата нужно показать пользователю.

### Ошибки

Обрабатывайте сетевые ошибки и не показывайте успех до успешного ответа. Backend возвращает для ошибок валидации и бизнес-правил `400`, для отсутствующего набора — `404`; обработчик API обычно передаёт пояснение в поле `message` (`{ "message": "..." }`). Также обработайте ошибки авторизации и другие неожиданные ответы средствами, принятыми во фронтенде. После ошибки сохранения сохраняйте введённые данные формы.

Предотвращайте повторную отправку одной операции, пока она выполняется; после операций, которые меняют наборы или активные значения, синхронизируйте отображение с сервером.

## Критерии готовности

- Кнопка находится **внутри выбранного расписания рядом с кнопкой запуска солвера** и видна администратору согласно существующим правилам доступа.
- Окно загружает серверные активные значения и `defaults`, позволяет изменять все 15 полей и применяет указанные ограничения.
- Работают создание, редактирование, активация, удаление наборов и восстановление системных значений; состояние активного набора соответствует ответам сервера.
- Пользователь видит, что настройки глобальны и их изменение не запускает пересчёт.
- Обработаны пустой список, загрузка, ошибки, несохранённые изменения и подтверждение удаления.
